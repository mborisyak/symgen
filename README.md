# symgen

symgen is an interpreter and a generator of symbolic expressions. It uses a stack-memory machine
for evaluation and a **DAG-first** stochastic process — a directed acyclic graph of memory-free
sub-expressions, each generated by a parameterized context-free grammar — for sampling random
expressions.

## Why?

For sampling large datasets of "low-complexity" regression and classification tasks generated by
symbolic expressions of limited size.

## Evaluation

### Assembly language

symgen uses [reverse Polish notation](https://en.wikipedia.org/wiki/Reverse_Polish_notation).
The instruction set comes from a library of operators and can be extended with custom ones.

```python
import symgen

machine = symgen.StackMachine(symgen.lib.core, symgen.lib.std)
```

Most operators have plain names (`add`, `mul`, `sqrt`, …). The **core operators** have special
syntax and operate on a flat, addressable **memory**:

- `<float | integer>`, e.g. `1.0` — `const`, pushes a constant onto the stack;
- `(i)` or `(name)`, e.g. `(0)` / `(x)` — `load`, pushes the contents of a memory cell onto the
  stack (the cell is left unchanged);
- `[i]` or `[name]`, e.g. `[1]` / `[y]` — `store`, pops the top of the stack into a memory cell.

**Inputs are memory.** The machine pre-populates the first `n_in` cells with the input variables,
so `(0)`, `(1)`, … read the inputs, and higher cells are scratch space. There is no separate
"input" instruction.

```
### 1 + 2
1.0 2.0 add
### sqrt(x^2 + y^2),  inputs in cells 0 and 1
(0) (0) mul (1) (1) mul add sqrt
### reuse a sub-result via memory:  let t = x + 1.5;  t * t
(0) 1.5 add [2] (2) (2) mul
```

`machine(expression, inputs=None, *, out=None, **kwargs)` evaluates a program. `inputs` is a numpy
array of shape `(n_in, *batch)`. Named inputs can be passed as keyword arguments instead:

```python
machine.evaluate('1.0 2.0 add')                                  # 3.0
machine('(0) (0) mul (1) (1) mul add sqrt', np.array([3., 4.]))  # [5.0]
machine('(x) (x) mul (y) (y) mul add sqrt', x=np.array([3.]), y=np.array([4.]))  # [[5.0]]
```

`machine.evaluate(expression, *inputs)` is a positional convenience wrapper.

**Named cells (sugar).** Inside `()`/`[]` an integer body is a numeric cell; an identifier is a
named cell. Names are resolved per call: named inputs (the `**kwargs`) occupy cells `0..n_in-1` in
order, then any name first seen in the program is assigned the next free cell. The generator never
emits names — they are a convenience for hand-written programs.

*Note:* arguments for multi-argument operators are taken from the top of the stack, so the order is
reversed relative to conventional notation: `f(arg_1, …, arg_n)` is `arg_n … arg_1 f`.

### Expression code

Programs are lists of operations — tuples of an operator name and an optional argument, e.g.
`[('const', 1.0), ('load', 0), ('add',)]`. `StackMachine` accepts both a string and a list.
`StackMachine.parse` turns a string into the list form (load/store addresses may be `int` or a
name `str`):

```python
machine.parse('(0) 1.5 add [1]')
# [('load', 0), ('const', 1.5), ('add',), ('store', 1)]
```

### Why a stack-memory machine?

Stack machines map naturally onto symbolic expressions: `(x + y) * z` → `x y + z *`. Their one flaw
is reusing sub-results — computing `p(x) log p(x)` on a pure stack duplicates `p(x)`. A small
addressable memory (`store`/`load`) introduces temporary variables and lets the generator express
**sharing**, which is exactly what the DAG model below produces.

### Extending the instruction set

Operators are **plain jax functions** — functional (no in-place `out=`): they take their operands
and return a fresh value. They are *not* individually jitted (jit is applied by the machine when you
`compile`). Provide a dictionary of them:

```python
import jax.numpy as jnp
my_library = dict(inc=lambda x: x + 1)
```

The op code is a tuple `('<name>', *arguments)`, and symgen inspects each function's signature to map
it (the machine is designed to compile to C, so the split is explicit):

- **operands** popped from the stack are the **positional** parameters (positional-only or
  positional-or-keyword); their count is the arity;
- the baked **`*arguments`** are the **keyword-only** parameters, filled in declaration order — e.g.
  `affine_add(x, y, *, wx, wy, b)` pairs with `('affine_add', wx, wy, b)`, and `const(*, value)`
  with `('const', value)`;
- `memory` is the one **reserved** keyword-only name: the machine injects its memory list (used by
  the core `load`/`store`), it is not a baked argument;
- varargs (`*args`) and `**kwargs` are forbidden.

An operator that pushes nothing (e.g. `store`) returns `None`.

### Compiling a program

`StackMachine` interprets a program op-by-op (eager jax). To fuse a whole program into a single
jitted callable `f(inputs) -> outputs`, use `StackMachine.compile` — since every op is a jax
function, this is just `jax.jit` over the interpreter:

```python
f = machine.compile(program, n_in=2)   # jax.jit-compiled
outputs = f(inputs)
```

`StackMachine.show(program)` renders a program as a readable expression for inspection.

## Generating random expressions

Generation has two layers:

1. a **DAG of nodes**, where each node is a memory-free sub-expression whose leaves reference the
   node's *inputs* (other nodes or true inputs); and
2. a **parameterized context-free grammar (PCFG)** that generates each node's expression.

Memory is never written by the grammar author — the driver lowers the DAG into `load`/`store`
automatically.

### The DAG layer

A topology *is* a **unified graph**: a flat, topologically-sorted `list` over one global
cell-index space (`Topology` is just an alias for `list[Node]`). `graph[i]` is either `None` (cell
`i` is a true input) or `(links, context)` for a computation node, where `links` are the global
cells (all earlier, so the graph is acyclic) the node may reference by local index, and `context`
is a `dict` of named variables the topology hands to the node grammar. What goes into `context` is
the topology's choice; how it is used is the grammar's (it is consumed by scope, exactly like
`rng`/`stack`/`memory`). The outputs are simply the **trailing `n_out` cells** — outputs are sinks
of a topologically-sorted graph, so they cannot be anything else (and they may not reference one
another).

```python
generator = symgen.GeneratorMachine(
  symgen.lib.core, symgen.lib.std, rules=rules,
  topology=symgen.RandomTopology(n_nodes=8, max_inputs=4),
)

program = generator.generate(rng, seed, inputs=inputs, n_out=1, attempts=None)
```

- `topology` — a `TopologyGenerator`, a **hyper-parameter of the machine** (like `rules`). It can
  be overridden per `generate` call. `RandomTopology(n_nodes, max_inputs)` links each node to a
  random `1..max_inputs` of the already-existing cells (and passes no `context`; the default
  `symgen.load` leaf picks one of a node's links uniformly). `n_nodes` may be an `int` or a
  `callable(rng) -> int`. Custom generators (e.g. layered) implement
  `__call__(rng, n_in, n_out) -> Topology`.
- `inputs` — a numpy array `(n_in, *batch)`; the first `n_in` memory cells.
- `n_out` — number of output nodes (the program leaves their values on the stack).
- the return value is a stack-machine program; `symgen.restore_topology(program)` reconstructs
  the (best-effort) topology for inspection.

The driver generates nodes in order, **tracing** each into a global memory so a node that
references an earlier node sees its real, already-computed value (see *Self-normalization*). It
then lowers everything: each node's local `load` indices are rewired to global cells, each node is
stored, and the outputs are loaded.

The DAG is **pruned twice** so the program carries no dead work: once after sampling the topology
(a node is generated only if some output can reach it through the candidate link pools), and once
before lowering (reachability is recomputed over the `load`s each expression *actually* emitted —
an expression may reference fewer cells than its pool offered, so nodes that turn out unreferenced
in the real code are dropped).

### The node grammar (PCFG)

Within a node the grammar is an ordinary PCFG. A grammar maps non-terminal **symbols** to
probabilistic transition tables over **expansions** (sequences of invocations and operators). The
only leaf that references the node's inputs is `symgen.load` — it samples one of the node's inputs;
there is no `variable` instruction and no manual memory.

```python
import symgen
from symgen import symbol, op, load

expr = symbol('expr').auto(depth=lambda depth: depth - 1)

rules = {
  expr.when(lambda depth: depth > 0): {
    expr() + expr() + op('add'): 1.0,
    expr() + expr() + op('mul'): 1.0,
    load: 2.0,
  },
  expr.when(lambda depth: depth <= 0): load,
}
```

The PCFG machinery (unchanged from a plain stochastic CFG, with these extensions):

- **Conditions** — `symbol.when(predicate)` gates a transition table on the node's context. When
  several conditions match, their tables are merged and likelihoods normalized jointly.
- **Invocations** — `symbol(var=update, …)` expands a symbol with a new context computed from the
  current one. Update functions are independent and use the *original* context; variables without
  an update are copied. `symbol.auto(...)` copies update functions into every invocation.
- **Parameterized operators** — `op(name, argument)`, where `argument` may be a function of the
  context (and of `rng`, `stack`, `memory`, and any topology-provided `context` entry).
- **Conditional likelihoods** — a likelihood may be a function of the context.
- **Local context** — `symbol.where(tmp=...)` introduces temporary variables, computed
  sequentially before the (independent) updates.
- **Random generator** — available as the `rng` keyword.

(Each node must net exactly one stack value — its output.)

### Self-normalization

A naive grammar produces NaNs, infinities, or wildly scaled values, and the risk grows with
complexity. symgen keeps values controlled with an invariant — **every value flowing between
operators is O(1)** (standardize the true inputs first) — enforced by normalizing each operator's
output as it is generated. This is what tracing is for.

The operators in `symgen.lib.affine` are generic affine forms that just *apply* coefficients, e.g.
`affine_exp(x; w, c, s, b) = s·exp(w·x + c) + b`. The coefficients are computed on trace by a
**normalization scheme** in `symgen.grammars.normalized`: it reads the current `stack` (the operands,
already O(1)), samples the random weights/shifts (`w`, `c`), and chooses the scale `s` and bias `b`
so the result is more-or-less standardized (zero mean / unit std, or a positive analogue). A single
operator can be driven by several schemes — `exp` subtracts the mean, `pos_exp` keeps the output
positive — both through `affine_exp`.

`symgen.grammars.normalized` exposes `add`, `mul`, `div`, `exp`, `log`, `square` and their `pos_*`
variants. The coefficients are sampled once at generation and baked into the program, so re-running
it on `StackMachine` reproduces the traced values exactly. Because nodes are traced in topological
order, a `load` of an earlier node pushes that node's already-normalized output, so normalization
**composes across the whole DAG**.

(Affine normalization controls *scale* but cannot bound heavy tails, so an occasional output has a
sharp spike — clip to a percentile range when plotting.)

### Rejection sampling

`assure(check)` (on symbols, invocations, conditions, operators) adds a post-expansion check that
sees the up-to-date `stack`/`memory`. If it fails, the expansion is retried until `attempts` is
reached (`attempts` argument of `generate`). A node's output is committed only once it passes.

```python
expr = symbol('expr')
rules = {
  expr.assure(lambda stack: np.std(stack[-1]) < 1.0):
    load + op('const', lambda rng: rng.exponential()) + op('mul'),
}
generator = symgen.GeneratorMachine(symgen.lib.core, symgen.lib.std, rules=rules,
                                  topology=symgen.RandomTopology(n_nodes=4, max_inputs=2))
program = generator.generate(rng, expr(), inputs=inputs, n_out=1, attempts=64)
```
